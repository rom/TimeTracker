# ADR-0018: The application can terminate TLS itself

* **Status:** accepted
* **Date:** 2026-08-18
* **Addresses:** ASR-003, ASR-005

## Context

Server mode carries passwords and session cookies. Both are worthless to an
attacker who cannot see them and decisive if they can, so the transport has to be
encrypted. The usual advice for a Go service is "put it behind nginx", and for a
large deployment that is right: the proxy handles certificate renewal, HTTP/2,
rate limiting and static assets.

But the premise of this application is a single self-contained binary
([ASR-003](../ASR.md)). A two-person consultancy that wants a shared timesheet on
one small server should not have to learn nginx to get HTTPS, and telling them to
run it on plain HTTP inside a "trusted" network is how passwords end up on the
wire.

## Decision

**Support both, and refuse the unsafe combination.**

`--tls-cert` and `--tls-key` make the process terminate TLS itself, with a
deliberately opinionated configuration: TLS 1.2 floor, and for 1.2 only the AEAD
cipher suites with forward secrecy. CBC suites carry a family of padding-oracle
attacks, and RSA key exchange has no forward secrecy - a stolen key would decrypt
last year's captured traffic as well as tomorrow's. TLS 1.3 suites are not
configurable in Go, by design, and are all sound.

Leaving both empty means a proxy is doing it, which stays fully supported.

**Server mode refuses to bind a non-loopback address** unless one of three things
is true: it has a certificate, `--secure-cookies` says TLS terminates upstream,
or `--allow-insecure` explicitly accepts sending passwords in clear. Serving a
login form over plain HTTP to a network is not a configuration this will fall
into silently.

Two supporting decisions:

* **The private key must not be group- or world-readable**, and the process
  checks rather than assuming. A key generated with a careless umask is a common
  and quiet mistake. Not enforced on Windows, where Go's reported permission bits
  are synthesised and say nothing about the real ACL.
* **HSTS is off by default** and enabled with `--hsts-max-age`. It is one of the
  few headers that is genuinely hard to undo: a browser that has seen it refuses
  plain HTTP to that host for the whole max-age, and a misconfigured deployment
  can be unreachable for months with no way to clear it remotely. That belongs to
  a deliberate operator decision, not to a default.

Certificates are generated by `scripts/gen-cert.sh` and `gen-cert.ps1`, in either
self-signed or local-CA form. Neither is offered as a substitute for a publicly
trusted certificate on an internet-facing host, and the scripts say so.

## Consequences

**Positive**

* A small team gets HTTPS with two flags and one script, and no second piece of
  software to operate.
* The cipher configuration is ours to state and to review, rather than whatever
  the proxy in front happens to have been configured with years ago.
* The refusal to serve plain HTTP publicly closes the most likely way this ends
  up deployed badly.

**Negative / accepted costs**

* No automatic certificate renewal. There is no ACME client in the binary, so a
  self-managed certificate is a recurring manual task - documented in
  `scripts/README.md`, and the reason a reverse proxy is still the better answer
  for an internet-facing host.
* No OCSP stapling, no HTTP/2 tuning, no request buffering: everything a mature
  proxy provides is absent.
* The TLS configuration is compiled in. Raising the floor to 1.3 later, or
  responding to a newly broken suite, needs a release rather than a config
  change.
* Two supported topologies means two sets of cookie and forwarded-header
  behaviour to get right and to test.

## Alternatives considered

**Require a reverse proxy** - simpler, and correct for large deployments.
Rejected on ASR-003: it makes the smallest useful deployment need a second
service and a person who knows how to configure it.

**Embed an ACME client for automatic Let's Encrypt certificates** - genuinely
attractive, and it would remove the renewal cost. Rejected for now as scope: it
needs port 80 or a DNS provider integration, both of which pull in configuration
and failure modes disproportionate to the current stage. A future ADR.

**Generate a self-signed certificate automatically on first run** - zero
configuration. Rejected: it trains users to click through certificate warnings,
which is a worse habit than any convenience it buys.
